# Engineering audit — 2026-11-12

## Scope and evidence

Reviewed the Java API, SQL migrations, React admin and player, Compose setup, demo gateway, and bundled sample media. Executed `mvn test` (9 tests), `npm run build` (TypeScript plus Vite), `npm audit` (0 reported vulnerabilities, including dev dependencies), `node --check public/sw.js`, `bash -n scripts/backup.sh`, and `docker compose config -q`. PostgreSQL integration and physical TV tests could not run because this machine's Docker daemon and external Docker data volume were unavailable during this audit.

The tests cover 20 shuffled cycles for each of three rounds, 16 unique exercise IDs per cycle, eight operating dates, closed/open time boundaries, admin session checks, signed media expiry and scope, and an HTTP byte-range response. These are code-level checks. They do not establish that a Samsung TV can decode two particular uploaded videos simultaneously.

## Functional and UX review

| Flow | Finding and change |
| --- | --- |
| Admin sign in | Added a password screen, 12-hour token, sign out, expired-session handling, and a failed-login limit. Passwords are supplied from environment variables. |
| Screens and pairing | Each screen retains its own token hash and round assignment. Pair codes are now unique, single-use, ten-minute values with a server-side attempt limit and an atomic claim. Unpairing revokes the token. |
| Content upload | The MIME type and actual MP4/WebM container header are checked. Uploaded files remain local, outside Git. The UI keeps edit forms open after a failed save. |
| Rotation | Eight persisted operating dates and two distinct exercises per date. Tests exercise 20 cycles in each of three rounds. Existing cycles remain fixed when the calendar configuration changes. |
| Memberships | Status is calculated only from start/expiry dates. Renewal must extend the current expiry and uses a compare-and-update query to detect simultaneous edits. The form defaults to 30 additional days. |
| Portrait player | Two muted videos remain stacked in a 9:16 layout. The player uses local Casablanca time at open/close boundaries, retains only the current day's content offline, and prefetches two clips of at most 50 MB each where the browser supports service workers. |

The dashboard's paired-screen label now describes pairing rather than live connectivity. There is no fabricated attendance, round completion, heart-rate, or workout-progress metric.

## Threat model and controls

| Threat | Current control and limit |
| --- | --- |
| Anonymous access to member and admin data | Every admin API route needs an explicit session header. API and PostgreSQL ports bind to localhost in Compose. The web port is still HTTP on the LAN; HTTPS is required before using untrusted networks or real member data. |
| Cross-site request forgery | The browser sends a custom header and no auth cookie. A cross-origin form cannot attach the token; the app does not enable cross-origin access. This follows the distinction in [Spring Security's CSRF guidance](https://docs.spring.io/spring-security/reference/features/exploits/csrf.html) between explicit headers and automatically sent browser credentials. |
| Device impersonation and pairing brute force | Random 32-byte device tokens are stored only as hashes; six-digit codes expire after ten minutes, are single-use, and are rate-limited. Rate limits are in memory and reset on restart. |
| Cross-device content access | `/api/player/content` derives the screen and round from the supplied device token. Media links are HMAC-scoped to the issuing screen, and the media endpoint verifies that the screen remains paired. This is a single-tenant deployment, not a multi-gym authorization model. |
| Public media and stale links | Media requires a signed link. Admin links last at most 30 minutes; device links at most 12 hours. Browser caches can retain content after unpairing until the current day ends. |
| Upload abuse | Multipart size is capped at 250 MB, extensions are generated by the server, and container magic is checked. There is no transcoding, malware scanning, or video codec verification. Supply only trusted media. |
| Injection and browser scripting | JDBC parameters are used for values; React renders text as text; nginx sends CSP, `nosniff`, and referrer restrictions. No `dangerouslySetInnerHTML` was found. |
| Secrets and supply chain | Runtime secrets are required from `.env` and ignored by Git. CI actions are pinned to commit SHAs; `npm ci` uses a lockfile; Dependabot checks npm, Maven, Actions, and Docker. `npm audit` found zero reported vulnerabilities on this date. These checks do not prove the absence of unknown vulnerabilities. |
| Data loss | PostgreSQL and media volumes are distinct. `scripts/backup.sh` streams each into an encrypted file. The backup script and restore path still need an operational test with a live deployment and a separate restore target. |

## Efficiency and architecture

The rotation uses a transaction-scoped PostgreSQL advisory lock per round, so competing API/device requests cannot create the same cycle concurrently. Database indexes cover member expiries, device token lookup, pairing code uniqueness, round/screen lookup, and rotation date lookup. The player polls every 30 seconds; the admin polls every minute. Signed display media URLs are stable over a six-hour window to avoid reloading videos on every poll. The production web container serves static files through nginx rather than Vite's development server.

The main pattern is MVC with a dedicated `RotationService` for cycle rules, `OperatingCalendar` for time policy, and `MediaSigner` and `AdminAccessFilter` for security policy. Constructor injection and the stateless `pairs` function keep rotation rules independently testable. The round/day schema is a persisted schedule snapshot of exercise IDs.

SOLID review: `RotationService`, `OperatingCalendar`, `MediaSigner`, and `AdminAccessFilter` each have one clear responsibility (SRP). Schedule pairing accepts a `Random`, allowing alternate shuffle strategies in tests (OCP/DIP). There is no inheritance hierarchy with an LSP risk. The small input records and separate security components avoid a broad interface (ISP). **The remaining `ApiController` still combines dashboard, exercise, screen, player, and member endpoints and directly depends on JDBC. Its SRP and DIP are only partially met.** It should be split into feature controllers and service/repository boundaries before expanding to multiple gyms or staff roles. This is an architectural limitation, not a claim of full SOLID compliance.

## Required deployment checks

1. Bring up Compose with real secrets and run a database-backed API smoke test: create a member, edit, renew, upload 16 videos, generate a code, pair three devices, unpair one, and confirm denial.
2. On the chosen TV model, verify simultaneous H.264 MP4 playback, range requests, portrait orientation, fullscreen, reconnect after a server restart, and offline playback of clips under 50 MB. Test a new operating day while disconnected: the old schedule must not display as current.
3. Test encrypted backup **and restore** to a separate instance. Keep the passphrase and backup copies off the gym laptop.
4. Add trusted HTTPS termination before remote admin use or transport of real membership details over an untrusted network. Add staff roles and an audit log if multiple operators or gyms are introduced.
